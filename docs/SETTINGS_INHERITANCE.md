# 設定の継承と運用（QW-20260924-004）

## 適用順位

対象項目の適用順位は **公演 → 組織内シナリオ → 店舗 → 組織共通 → 標準値**。
設定画面は適用値と設定元を表示する。「共通設定を使う」は、その対象の個別指定を解除して下位の値を使う。

- 未登録キーは従来の列を参照する。移行前の実効値を維持するための互換性であり、新規保存は差分テーブルを使う。
- `null` は明示的な継承。従来列に値があってもその値を復活させない。
- `0`、`false`、空文字、空配列は明示値。配列は項目単位ではなく全体を置換する。
- 対象と組織の所属をサーバーで検証する。スタッフは閲覧、管理者は保存可能。revisionによる競合時は409を返す。
- 会社名・連絡先など組織／店舗の識別情報は組織共通・店舗のみ。物理的な定員、認証情報や接続先はこの継承対象ではない。

## 対象と実際の適用先

| 対象 | 適用先 |
| --- | --- |
| キャンセル規定・料率・変更期限 | 公開規定、予約時snapshot、マイページと人数変更受付 |
| 支払い方法の名称・案内 | 予約確認画面 |
| メール文面・会社連絡先 | 予約、変更、中止、貸切、キャンセル待ち、開催判断、リマインドの各送信経路 |
| リマインドの有効／無効・日数・時刻 | JSTの送信予定、永続的な送信claimとプロバイダの重複防止キー |
| 開催の最終判断時刻 | DBの判定、公開予約可能期間、前日案内、毎分の対象抽出 |
| 準備時間 | 公開空き表示・送信直前・申込／承認DB・スタッフ保存／移動／複製の前後公演の間隔 |
| 事前配役アンケート | 管理一覧、承認／案内、グループ画面、参加者回答、案内済み期限 |

準備時間は合計分数。従来の追加準備時間は、個別指定を解除するまでは従来の基本60分を足した値として扱う。
前後の公演の準備時間は、それぞれ後に始まる公演の設定を使い、日付境界も検査する。スタッフの例外配置には既存の確認フローを維持する。

## 既存条件の維持

- 既存のキャンセルsnapshotは更新しない。
- 予約変更期限は新規申込時に保存する。既存予約のNULLを遡及補完しない。期限後の顧客による人数変更は拒否し、同じ組織のスタッフ／管理者は例外対応できる。
- 追加募集の案内済み期限を優先する。前日延長で決めた開催判断期限も別表で固定する。
- アンケートの案内済み月日を復元して固定し、新規案内は送信前に期限を固定する。
- 旧メール取得で行っていた「別店舗の非空値で補完」は移行時に実効値を保存する。以後は組織共通を明示して参照する。
- 自動リマインドの移行初期値は、実稼働していた前日9時。以前の未使用UI値で突然送信時刻を変更しない。

1. DBの150000～153000、155000～161000を適用する。154000と162000はまだ適用しない。
2. 共通処理を使う変更対象Edge Functionsを配備する。

4. フロントエンド／Node APIを反映する。ready、対象commit、正しいドメイン、設定画面・読取APIを確認する。
5. 本番も同じ順序。既存の外部定期実行と併存しても、判断ログ・公演ロック・送信claimで二重処理を避ける。

初回公開前に戻す場合の手順は `docs/rollback/qw-20260924-004-settings-hierarchy.sql`。
保存済み設定や新規予約へ適用後は、その値を保持するforward migrationを使う。ロールバックSQLは新規予約への適用や設定編集がある場合に中断する。
