# 構造上の追加欠陥の修正（QW-20260917-001）

Studio保存元アトラスを起点に、2026-09-21の本番定義と現在のAPIを照合した。GM ID保持・給与のPR493とは別の差分として扱う。

1. ライセンス集計: `license_performance_summary` は内部公演と外部報告を明細のまま結合し、内部公演や組織別作品の行数だけ外部回数が増えていた。`api/external-reports.ts` のlicense_admin専用サマリーで使われている。内部・承認済み外部を先に集計し、金額ごとの設定も重複排除してから結合する。既存の全組織集計範囲、異なる金額の行、列型・権限を保持する。請求確定額や契約版の設計変更は含まない。現時点の本番外部報告は0行で、実際の過請求があったとは判断しない。staging試行の現行結果差分は、金額0円・同じ回数のテスト作品重複1行の解消だけだった。
2. 予約索引: `idx_reservations_event` と `idx_reservations_schedule_event_id` は同一btree(schedule_event_id)。重複側に制約・依存オブジェクトがないことを確認した。定義一致をSQL内でも再検証し、重複側のみ削除する。予約行は変更しない。本番での重複索引サイズは696kB。
3. キット移動: APIはorg_scenario_idのみ送るが、必須scenario_master_idへの変換がなく作成に失敗する。完了トリガーも削除済みscenario_idと存在しない旧一意制約を使っていた。組織別作品からmaster IDを同一トランザクションで補い、組織・店舗・IDの整合を検証する。完了時は既存の組織別作品・キット番号の一意制約で現在位置を更新し、破損状態等は保持する。master必須の既存制約と矛盾するON DELETE SET NULLをRESTRICTに揃える。現時点の本番移動予定は0行。新しい個体マスタは作らない。

回帰検証: ライセンス明細の複数結合、同じ回数の別報告、承認/未承認、中止、内部0件、同額/異額設定、空作品、列型/権限保持、索引の定義検査と復旧。キットの旧失敗を再現し、現ID/旧ID作成、完了、再完了、現在地、属性保持、別組織、ID不一致、必須項目、master削除、途中失敗ロールバックを検証した。staging実DBでも架空キット番号の作成から完了まで実行し、全操作をROLLBACKした。

DB先行: 20260921121000・20260921122000・20260921124000をstaging適用・読戻し済み。本番はまだ未適用。SQL・復旧は同時刻名のsupabase/migrations・supabase/rollbacksに保持。kit API変更の配備前にDB適用が必要。
