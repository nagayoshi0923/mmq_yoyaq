# QW-20260907-005 公演ごとの追加募集期限

## 管理者による個別期限の設定

`PATCH /api/schedule?action=extend-recruitment&id=<公演ID>` に、タイムゾーン付き `deadline` と `reason` を渡す。管理者のみ。組織IDは認証済みユーザーから決め、DBでも公演との一致を検証する。AI Managerのサーバーはservice role専用の `set_performance_recruitment_deadline` RPCを使用できる。

```json
{"deadline":"2026-09-08T12:30:00+09:00","reason":"最低開催人数まであと1人のため追加募集"}
```

このJSONの日時は管理者APIの書式例。自動運用の開始90分前ルールは以下に定義する。指定期限は現在より後、公演4時間前以降かつ開始前が必須。予約の増加履歴は条件にしない。開催未決定・以前に開催確定ログのある公演の両方を扱う。中止済みは自動復活させない。

新しい判定RPCをEdge Functionの4時間前処理から呼ぶ。人数未達でも明示した期限前なら中止しない。人数が揃えば4時間前以降の次回判定で確定し、期限到達後も不足していれば従来の中止通知処理へ渡す。cron停止後の復旧で開始時刻を過ぎていても、期限付き公演は取り残さない。公演の行ロック・終端状態によって重複実行を防ぎ、以前の開催確定ログは上書きしない。

期限・理由はservice role専用テーブルに保存する。公開公演テーブルに内部の判断理由を追加しない。同じ要求の再送は同じ結果を返す。案内済み期限を変える専用フローは今回含まず、異なる期限への上書きを拒否する。

## 承認済みの自動運用

4時間前の判定時に、最低開催人数まであと1人または2人なら開始90分前まで追加募集する。予約増加履歴を条件にせず、開催未決定・開催決定後の欠員の両方を対象とする。人数が揃えば次の毎分判定で開催確定、期限未達なら中止する。既に案内した期限は途中で不足人数が変わっても変更しない。

組織別 `performance_recruitment_policies` の `one_seat_enabled` は既存の有効化フラグ名として維持する。`max_missing_participants` は1または2で、migration直後は1。新しいメール処理を配備してから、承認済み組織だけ2に変更する。3人以上は今回の自動延長条件に含めない。既に中止済みの公演は復活させない。

自動延長開始時には予約者と不足人数をsnapshotへ保存し、期限・専用リンク・無料辞退をメール案内する。無料辞退は開始時点の予約者が開催判断待ちの間に確認操作した場合だけ。元のキャンセル者や後からの予約者を免除しない。開始・最終結果・辞退受付の通知はoutboxで再試行し、送信の冪等性キーで重複を防ぐ。

管理者による任意期限設定APIは、この自動対象選択とは別経路であり、開始メールを自動作成しない。個別利用時は顧客案内を別途確認する。任意期限の管理画面編集・通知失敗後の社内エスカレーションは残る整備事項。

## 反映順と復旧

DB migrationを先に適用・検証してからEdge FunctionとAPIを反映する。他の未適用migrationをまとめて適用しない。旧RPCを直接呼ぶcronが残っていないことと、新しい期限に間に合う実行頻度を確認する。

ロールバック時は、活動中の延長がないことを確認したうえでEdgeの呼出先を `check_performances_four_hours_before` に戻し、APIの新規設定を停止する。活動中の延長を残したまま戻すと案内済み期限より早く中止されるため禁止。テーブルと履歴は削除せず保持する。

## QW-20260907-005: 開催判断と予約受付締切を分離（2026-09-08）

開催決定は最低開催人数への到達であり、満席とは限らない。追加募集の開催判断期限（90分前）と、開催決定後の空席の予約受付締切を分離する。既存店舗設定と既存公演制限を標準として保持し、公演別 `booking_cutoff_minutes` 指定はそれらを上書きする。NULLは標準継承、0は開始まで、1〜1440は開始前の分数。既存値を一括書換しない。

公演詳細「募集・締切」で両期限・判断状態・標準値・公演別設定を表示。管理者のみ独立保存でき、組織境界とupdated_at競合を検査する。開催判断期限はこの保存で変えない。顧客の予約確認画面にも現在の受付締切を表示する。DBと予約送信前チェックは共通の締切RPCを使い、activeの追加募集だけ案内済み期限を優先、開催決定後は通常受付へ戻る。

検証: 対象SQLと既存追加募集回帰、API9件（権限/組織/競合/入力）、画面の指定保存と標準復帰・390px横溢れなし、型/lint/build。migration `20260908010000_booking_cutoff` はDB先行。対象はDBとWeb、Edge変更なし。

復旧は旧予約トリガー定義とWebコードへ戻す。追加列は値と履歴を保持して残す。公開RPCは顧客/社内理由を返さない。
