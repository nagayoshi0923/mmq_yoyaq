## 1. 「予約」タブ

### サブタブ

「一般公演」「貸切」「キャンセル済み」の 3 つ。

- **一般公演**には貸切を出さない。貸切とは次のどれかに当てはまる予約:
  - `reservations.reservation_source` が `web_private`
  - `reservations.private_group_id` がある
  - 公演（`schedule_events`）の `category` が `private`、または `is_private_booking` が真
- 貸切はすべて「貸切」サブタブへ。

### 貸切サブタブ: 1 貸切 = 1 カード

- グループ（`private_groups`）と申込・予約（`reservations`）を結合して 1 枚にする。
  結び方は `private_groups.reservation_id` = `reservations.id`、または `reservations.private_group_id` = `private_groups.id`。
- グループの無い旧い貸切予約は、予約だけで 1 枚にする。

### 節と並び順（上から）

1. **あなたの対応が必要** — 自分に行動があるもの（下のラベル 1〜3）
2. **店舗の返事待ち** — 申込済みで店舗の確定を待っているもの
3. **主催者の準備待ち** — メンバーとして参加していて、主催者が候補日の登録・申込を進めるのを待っているもの（該当があるときだけ出す。段階 1 で追加した節）
4. **確定した貸切** — 公演日が今日以降の確定。日付の近い順。2 件まで出して「あと ○ 件表示」で展開
5. **終了した貸切・取り下げた申込** — 折りたたみ（既定は閉じる）。終了＝公演日を過ぎた確定。取り下げ・キャンセル済みは「キャンセル済み」サブタブに出すので、ここには件数だけ

### カードのヘッダー（左のラベル＝次にやること）

状態名ではなく **次にやること** を出す。判定の優先順:

1. 「主催者の引き継ぎに同意する」（段階 3 で使う。段階 1 ではラベル定義のみ）
2. 「事前配役アンケートに回答する」（確定後・公演日が今日以降・自分に未回答の事前配役アンケートがある）
3. 日程まわり（グループが `gathering` / `date_adjusting` のとき）
   - 「候補日を決める」: 主催者で、候補日が 0 件
   - 「日程に回答する」: メンバーで、自分が未回答の候補日がある
   - 「申込に進む」: 主催者で、候補日がある（全員回答済みを含む）・未申込
4. 「店舗の返事待ち」（グループ `booking_requested`、または予約が `pending` / `pending_gm` / `gm_confirmed` / `pending_store`）
5. 「○/○(曜) 開催」（確定・公演日が今日以降）
6. 「終了」（確定・公演日を過ぎた）

補足: メンバーで回答済み（または候補日 0 件）のときは「主催者の準備待ち」（節 3）。

ヘッダー右は「あなたが主催」／「○○さんが主催」。その右に「操作」ボタンの置き場所（中身は段階 2。段階 1 では出さない）。

色はデザイントークンに従う。要対応＝紫系（貸切の色）、返事待ち＝琥珀系、確定＝緑系、終了＝灰色系。

### カードの中

- サムネイル、作品名
- 5 段階の進み具合: 招待 → 候補日 → 回答 → 申込 → 確定。確定後は「確定 → アンケート → 当日」に切り替え
- 1 行の説明文（例「候補日 2 件で申込中。店舗が日程を確定すると連絡が届きます」）。旧表示の「申込内容: 〜」「候補日 N 件で申込中」はここに統合
- 主ボタン 1 つ（次にやること）＋副ボタン「グループを開く」
- カードのどこを押してもグループページ（`/group/invite/{invite_code}`）へ。グループの無い旧い貸切予約だけ予約詳細（`/mypage/reservation/{id}`）へ

## 2. キャンセル済みサブタブ

- 貸切の取り下げ・キャンセルは **候補日を日付として出さない**（候補 1 件目が確定日のように見えるため）。
  申込中に取り下げたものは「候補日 N 件で申込中だったもの」と出す。確定後にキャンセルされたものは公演日を出してよい。
- ラベルを分ける（`reservations.cancellation_reason` で判定）:
  - 「取り下げ」: `PRIVATE_REQUEST_WITHDRAWN_REASON`（お客様による貸切申込の取り下げ）
  - 「店舗都合でキャンセル」: 店舗の却下（`貸切リクエストを却下しました`）、人数未達による公演中止（`人数未達による公演中止…`）
  - 「キャンセル」: お客様都合（`お客様によるキャンセル` など）と、判断できないものすべて

## 3. ヘッダー

お客様（`users.role = customer`）には名前の横の役割バッジ「顧客」を出さない。スタッフ・管理者・MMQ運営には従来どおり出す。

## 9. 赤い操作と確認ダイアログ（影響を数字で見せる）

### 「グループを閉じる」1 つにまとめた理由と内部処理

旧画面は「グループをキャンセル」（`cancel_unrequested_private_group`、状態を `cancelled` にするだけ）と「グループを削除する」（`delete_private_group`、候補日・回答・チャット・メンバーの行を消す。`gathering` のみ）の 2 本立てだった。

- 「グループを閉じる」は **`cancel_unrequested_private_group` 側（行を消さず履歴を残す）** を使う。理由: 日程調整中（`date_adjusting`。却下後の再調整を含む）でも使える／チャット・回答の記録が残り、問い合わせや店舗側の確認に使える／取り下げ・キャンセルと同じく「閉じた状態」で揃う。
- `delete_private_group` は画面から使わなくなった（RPC 自体は残す）。
- 閉じたグループの招待ページは「このグループは閉じられています」を出す。

### メンバーへの知らせ方（段階 2 時点）

- 「知らせる」＝グループのチャットに記録を残すこと（取り下げ・キャンセルの既存処理 `cancel_reservation_and_group_with_notice` と同じ方式）。閉じたグループの招待ページでも閉じたことが分かる。
- メール・プッシュでメンバーへ届ける仕組みは **段階 4（通知の整備）** で扱う。

# 段階 3（2026-10-09 決定・実装）主催者の引き継ぎ（案 B）

## 14. 考え方

- グループを作った時点で予約サイト上の契約は始まっている。引き継ぎは「契約者（申込者）の交代」として扱い、**新主催者の同意で成立**する。
- 申込前・申込後（店舗の返事待ち）・確定後のいずれでも使える。宛先は会員（アカウントのあるメンバー）だけ。ゲストには引き継げない。
- 依頼は 1 グループに同時 1 件まで。期限は 72 時間（依頼行の `expires_at`）。同意するまで元主催者のまま。

## 15. 流れと画面

| 場面 | 元主催者（依頼した人） | 新主催者（宛先） |
|---|---|---|
| 依頼 | メンバー管理シートの会員の行の「主催者にする」→ 確認「○○さんに主催者の引き継ぎを依頼します。○○さんが同意するまで、あなたが主催者のままです。依頼の期限は 72 時間です。」 | — |
| 知らせ | — | 通知ベル（`user_notifications`、`type=system`、リンク `/group/invite/{code}?sheet=handover`）／グループチャットの本人だけのお知らせ（個別お知らせと同じ表示・読み取り制限）に「確認する」 |
| マイページのカード | ラベル「○○さんの同意待ち（主催者の引き継ぎ）」（節はそのまま）。本文に期限。操作メニューに「引き継ぎの依頼を取り消す」 | 「あなたの対応が必要」節、ラベル「主催者の引き継ぎに同意する」、本文に誰からか・申込者（店舗への連絡先・キャンセル料の負担者）になること・期限。主ボタン「内容を確認して同意する」、副「引き継がない」 |
| メンバー管理シート | 依頼中は上に案内、宛先の行に「主催者の引き継ぎの同意待ち」。依頼中は「主催者にする」を出さない | — |

- メールは段階 4 で足す（DB 関数の送る場所にコメントを残した）。

### 引き継ぎ確認画面（グループページ `?sheet=handover`、`HandoverScreen.tsx`）

上から: 依頼の案内（誰から・申込者になる・同意まで元主催者のまま・期限）→ 引き継ぐ貸切（作品・状態・候補日〔申込前はグループの候補日、返事待ちは申込時の候補日〕または確定日時と会場・参加人数・料金・いまの申込者・予約番号・メンバー一覧〔自分を強調〕）→ あなたの連絡先（お名前・電話番号。新主催者の顧客情報から初期値、直せる。申込者として店舗に伝わる旨）→ 注意事項とキャンセルポリシー → 同意のチェック「注意事項とキャンセルポリシーを確認し、この貸切の申込者として引き継ぐことに同意します」→「同意して主催者を引き継ぐ」／「引き継がない（依頼を断る）」。

## 16. 成立（同意）時の一括処理（`private_group_handover_accept`、1 トランザクション）

1. `private_groups.organizer_id` を新主催者へ。`private_group_members.is_organizer` を入れ替え（旧主催者はメンバーとして残る）
2. 取り消されていない申込・予約があれば `reservations.customer_id / customer_name / customer_phone / customer_email` を新主催者へ（旧値は依頼行の `previous_customer` と予約の変更履歴 `reservations_history` に残る。キャンセル規定のスナップショットはトリガーで保持され変わらない）
3. チャットに「主催者が○○さんから○○さんに変わりました」（`organizer_handover` / `accepted`）
4. 店舗へ知らせる: 段階 2 の人数変更と同じ `discord_notification_queue` の `private_cancellation`。「貸切の申込者（契約者）が変わりました。作品・予約番号・状態・申込者：旧 → 新・新しい連絡先」。申込があり、チャンネルが設定されているときだけ
5. 依頼を `accepted` に。`accepted_contact`（氏名・電話・メール・顧客 id）、`accepted_policy`（固定版なら版と内容、未固定なら画面に出した現在の規定）＋同意日時を記録
6. 両者に通知ベル

連絡先の顧客情報は貸切申込と同じく画面で `upsertOwnCustomer` してから渡す（共通〔組織なし〕かグループと同じ組織の、本人の顧客行だけ受け付ける）。

## 17. 断る・取り消す・期限切れ

- 断る（宛先）・取り消す（依頼した人）・期限切れ（72 時間）。いずれも両者に通知ベル＋チャットに記録（`organizer_handover` / `declined`・`cancelled`・`expired`）。
- 期限切れは定期ジョブを使わず、**読み取り時**（グループ読み取り・マイページ・確認画面・各操作の前）に判定して `expired` に寄せる（`private_group_handover_settle`）。宛先が抜けた・外れた／グループが閉じた／主催者が変わった依頼も同じ所で `cancelled` に寄せる。

## 18. 立場の判定・承認画面

- マイページの「あなたが主催」「○○さんが主催」とメニューの立場は `private_groups.organizer_id` で決める（段階 1 はメンバー行の印を見ていたので、`summarizePrivateGroup` を organizer_id 優先に直した）。

## 23. 仕組み

- **ベル**: DB のトリガーで作る。
  - 予約: 申込の作成（貸切）、取消（`status` が cancelled へ）、人数の変更（一般公演）。
  - 貸切グループ: チャットのシステムお知らせ（`member_joined` / `candidate_dates_added` / `schedule_confirmed` / `booking_cancelled`）から。**コミット時に動く**（承認のあとにアンケートの締切を固める、取消で予約とグループを続けて閉じる、などの順番に左右されないため）。グループの状態（確定・閉じた）を確かめてから出すので、お知らせの形だけを真似た書き込みでは出ない。
  - そのほか: 開催決定メールの送信済み、リマインドの送信済み、クーポンの付与、アンケートのリマインドを積んだとき、段階 3 の引き継ぎのベル（→メール）。
- **メール**（新しく足したものだけ）: 送信待ちの表 `customer_notice_emails` に、積んだ時点の件名・本文で積む。5 分ごとの送信処理 `process-customer-notice-emails`（Edge Function。形はアンケートのリマインドと同じ。Resend・`email_logs`）が送る。本文の URL は `{{SITE_URL}}` で積み、送るときに置き換える。
  - 文面: 「○○ 様」→ 本文 →「▼ 詳しくはこちら」の URL →（ゲストのみ）PIN の案内 → 問い合わせ先 → 署名（組織のメール設定の会社名）。返信先は組織の返信先 → 会社の連絡先。絵文字なし。日付は既存のメールと同じ「2026年10月25日(日)」。
  - 宛先: 会員はログインのメール（無ければ顧客のメール）、ゲストは参加時のメール、取り下げの控えは予約のメール。
  - **送信の有効化**: `app_config` の `customer_notice_email` が `on` の環境だけ送る（取り出し関数と定期実行の両方で確認）。staging は本番の写しでログインのメールが実在のため `on` にしない。本番は送信処理を配備してから `on` にする。
- **押した先**: 一般公演は予約詳細 `/mypage/reservation/{id}`、貸切はグループページ `/group/invite/{code}`（候補日 `?tab=schedule`、アンケート `?tab=survey`、引き継ぎ依頼 `?sheet=handover`）、クーポン `/mypage?tab=coupons`、プロフィール `/mypage?tab=settings`、外された本人 `/mypage?tab=reservations&sub=private`。
- ベルの UI は既存のまま（既読・すべて既読・一覧 20 件）。人数変更のアイコン、空のときの文言だけ足した。
