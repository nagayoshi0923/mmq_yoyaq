## 1. v1 から何が変わるか

変わること
- 順番。DB が最初（v1 では3番目）。
- 完了の定義。「ファイルが小さい」ではなく「DB がリポジトリから再現でき、同じ事実が1か所にしか無い」。
- ファイル分割は最後に回し、書き込み経路の API 5本だけに絞る。画面の分割はやらない。

変わらないこと
- 先に滞留している作業を着地させる（Phase 0）。
- 挙動を変えない作業は CI 緑で即マージ。本番反映と実機受入を1件ごとに挟まない。
- 終わりを数字で決める。新しい発見は issue にして今の PR に混ぜない。

訂正
- Codex の2週間の方向（正本を1つにする、保存を1トランザクションにする、旧入口を閉じる）は、この着地点に合っていた。問題は方向ではなく、終わりの定義が無いことと、ずれたデータの補正判断が社長に戻ってきていないこと。

## 2. 「意図しない変更」が起きる原因（証拠つき）

1. 同じ事実が2か所に保存されている。
   - 旧GM配列 と 担当表: 19スタッフ176件がずれている。
   - 申請候補日 と 公演日時: 将来確定467件中43件が不一致。
   - ScheduleEvent 型が3か所で定義されている。
   - GM の照合が、給与計算は staff.name、担当は ID で別。
   - 予約金額の正本（入金・返金・クーポン控除後）が未決。
2. DB がリポジトリから再現できない。
   - 本番165表のうち、migration に CREATE TABLE があるのは103表。参照定義 schemas/ は55表。
   - RPC は migration に238個、参照定義 rpcs/ に122個。
   - アトラスは手作業の写しで、生成スクリプトはリポジトリに無い（README に明記）。
   - CI にあるのは「migration が適用済みか」の照合だけ。本番の構造とリポジトリの差を検知する仕組みが無い。
3. 画面・部品・hook から DB を直接触る箇所が22ファイル66箇所。API を直しても画面側の直接経路が残る。
4. 使われていない表が残っている。本番165表のうち、コードから参照ゼロが40表、1ファイルだけが19表。
   - 参照ゼロの例: game_* 14表、scenario_clues / scenario_phases / scenario_reviews など旧作品系、staff_scenario_assignments_backup_20260603、customers_org_backfill_20260707、reservations_history、system_settings。
5. ずれたデータの補正判断が止まっている。Codex は「推測で補正しない」を守り、ずれを全部そのまま残している（第5節）。

1. 挙動を変えない PR は CI 緑で即マージする。staging で寝かせない。実機受入と独立レビューを要求しない。
2. 挙動を変える PR（バグ修正）は別 PR にし、従来の手順で進める。
3. 1 PR は1ファイルか1責務。移動は600行以内。
4. 「全体IN_PROGRESS」の台帳追記をやめる。PR が issue を閉じる。
5. 作業中に見つけた別の問題は issue にする。今の PR に入れない。
6. 報告は1日1回。「マージした数 / 残り / 止まっている理由」の3行だけ。
7. 完了の判断は第3節の表だけで行う。
8. DB の変更は baseline 以後、migration と rollback の対でしか出さない。
9. ずれたデータを見つけたら直さず、「表・件数・意味・選択肢」の4点で第5節の表に追記する。

## 7. この方針そのものへの指摘

意図（意図しない変更を無くす、開発をやりやすくする）は正しい。優先順位も正しい。方法「DB をアトラスで確認しながら適正にする」は半分正しく、半分足りない。

### 7-1. アトラスは「あるべき姿」ではなく「今の写真」

アトラスは本番 DB から作った構造の写しであり、本番と照合済みという意味で正確。ただし「何が正しいか」は書いていない。候補日の表は履歴なのか正なのか、予約金額の正本はどの列か、旧GM配列は捨ててよいか。これはアトラスでは決まらず、社長にしか決められない。

Codex が2週間で終わらなかった直接の原因はここにある。ずれを見つけるたびに「推測で補正しない」ルールに従って判断を社長へ戻し、判断が出ないので項目が閉じない。方法を変えなくても、「判断を週1回まとめて出す」「出なければ『そのまま』で閉じる」と決めれば終わる。逆に、判断を出す時間が取れないなら DB の正しさを目標にしてはいけない。終わらない。

言い換えの提案: 目標2を「DB を正しくする」から「DB がリポジトリから再現でき、ずれたら CI が落ちる」に変える。正しさは終わりが無いが、再現できるかどうかは白黒がつく。再現できれば、意図しない変更は「起きない」のではなく「起きたら気づく」になる。それで十分。

### 7-2. 意図しない変更の原因の半分は DB ではなく進め方

今の証拠で見える原因のうち、DB 構造で説明できるのは二重保存と直接書き込みの分だけ。残りは進め方の問題。

- staging と main が142ファイルずれ、migration 11本が staging にだけ入っている。環境がずれていれば、どんなに DB がきれいでも「staging で動いたのに本番で違う」が起きる。
- 9/7 から91ファイルの作業が PR #431 に溜まり、その間に main が146 PR 進んだ。古い作業を後から入れれば、意図しない変更になる。
- Codex、Cursor、Claude の複数エージェントが同じリポジトリを同時に書いている（Codex レーン、Cursor の PR、Astra 設計と Sol 実装）。同時に書けば、片方の変更がもう片方を握りつぶす。
- ローカルの mmq_yoyaq は181コミット遅れの feature ブランチのまま。古い状態から作業を始める入口が残っている。

DB だけ直してもこれらは残る。Phase 0 を「片付け」ではなく「進め方の変更」として扱うべきで、具体的には次の3つ。
1. 整備期間中は mmq_yoyaq に書くエージェントを1つにする。並行させるなら、触るディレクトリを分けて重ならないようにする。
2. 毎日 main に着地させる。7日以上開いている PR は閉じる。
3. staging と main を常に一致させ、migration は両環境へ同じ日に適用する。

### 7-3. 「開発しやすい」の相手はエージェント

今の開発者は社長とエージェント（Codex、Cursor、Claude）。エージェントにとって開発しやすいとは、ファイルが小さいことより次の4つ。
- 見る場所が1つ（アトラスがリポジトリから自動生成される）。
- 変更の影響範囲が狭い（境界が lint で強制される）。
- 検証が速い（今は verify が7段、CI が34段、単体1,280件。遅いと検証を飛ばす誘惑が出る）。
- 古い状態から始められない（ブランチが少ない、main が常に最新）。

だから画面のファイル分割は後回しでよく、境界と再現性を先にするのが正しい。v2 の順番はこの判断に基づく。

### 7-4. 結論

- 意図: 正しい。
- 方法: DB を起点にするのは正しいが、「正しさ」ではなく「再現性と検知」を目標にし、同時に進め方（1人が書く、毎日着地、環境一致）を変えないと、DB だけ直しても意図しない変更は止まらない。
- 社長の役割: ずれたデータの判断を週1回まとめて出すこと。これが出ないと DB の整備は終わらない。

## 9. 整備期間の区切り（2026-10-02）

社長の「今日中に終わらせたい」により、整備期間（書き込みを Claude 窓口に一本化する期間）は 2026-10-02 で終える。以後は通常の不具合修正と機能開発に戻り、整備の残件は issue 単位で通常の作業として進める。残る決まりは次の4つだけで、docs/IMPROVEMENT_HANDOFF.md の先頭にも書く。

1. migration は rollback と対で出し、staging と本番へ同じ日に適用し、適用した環境の supabase/structure/<env>.json を同じ PR で更新する。手で片方の環境だけに当てない。
2. 毎日の drift チェックが落ちたら、その日のうちに migration で記録するか DB を戻す。黙って JSON だけ直さない。
3. staging と main の間の取り込みは merge commit で行う（squash は祖先関係を失う）。7日以上開いた PR は閉じる。
4. 完了の判断は第3節の表で行う。進捗の台帳追記に「全体IN_PROGRESS」は書かない。
