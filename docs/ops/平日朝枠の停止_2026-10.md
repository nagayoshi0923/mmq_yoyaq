# クインズワルツ 平日朝枠の停止（データ修正）の適用と復旧 2026-10

issue #1200 / PR #1201。社長の意図「平日は昼・夜のみ、朝枠は出さない」を、店舗の営業時間設定（データ）で反映する。
**これは migration ではない。#1201 をマージしても適用されない。本番で手動で当てるまで、東京・埼玉の 7 店の平日朝は選べるまま。**

- 修正 SQL: `supabase/data-fixes/20261021_queens_waltz_weekday_morning_off.sql`
- 照合 SQL（読み取りのみ。当てる前・後・復旧後のどれでも流せる）: `supabase/data-fixes/20261021_queens_waltz_weekday_morning_off_check.sql`
- 復旧 SQL: `supabase/data-fixes/20261021_queens_waltz_weekday_morning_off_rollback.sql`
- 試験（手元の使い捨て DB・架空データ。最後に巻き戻す）: `supabase/tests/data_fix_queens_waltz_weekday_morning_off.sql`（`npm run test:rpcs` に含む）

## 何を変えるか

`business_hours_settings.opening_hours.<monday〜friday>.available_slots` から `"morning"` だけを外す（設定 › 店舗別 › 営業時間 で平日の「朝」を消灯したのと同じ）。

- 対象の曜日: 組織 `queens-waltz` の行で、月〜金・営業日（`is_open` true）・開店 13:00 以降（朝に営業していない日）・`available_slots` に朝がある・朝を外しても枠が残る曜日だけ。開店が 13:00 より前の曜日（朝に正当に営業している日）は対象外。
- 変えない: 土日、開店・閉店時刻、枠の開始時刻（朝 10:00 の設定も残す。無効な枠では使われない）、休業日・特別営業日・特別休業日、札幌店（組織 `queenswaltz-sapporo`）と他の組織、既存の候補日・申請中・確定済みの予約の行。
- 安全装置: 変える曜日が 0 件（適用済み）か 35 件（7 店 × 5 曜日）以外なら中止して何も変えない。2 回流しても同じ（2 回目は 0 件）。
- 退避: 同じ取引の中で、変える行を `archive.business_hours_settings_backup_20261021`（id, store_id, opening_hours, updated_at, backed_up_at）へ保存してから更新する。ブラウザの役割（anon・authenticated）からは読めない（`archive` スキーマの USAGE も表の権限も無い。RLS・FORCE RLS 有効・ポリシー 0）。既にある退避行は上書きしない。
- 退避表を `public` ではなく `archive` スキーマに置く理由: DB 構造の記録（`scripts/db-structure-snapshot.mjs`、`supabase/structure/<env>.json`）と定期 DB Drift は `public` だけを見る。`public` に作ると「未記録の表の追加」で Drift が失敗し、環境ごとに構造を取り直す PR が要る。`archive` は既存の退避表の置き場所（migration 20261002120000 で本番・staging とも作成済み、PostgREST に非公開、2026-10-21 読み取りで anon・authenticated の権限なしを確認）なので、退避表を作っても残しても構造の記録は変わらず、取り直しは不要。
- 取引: ファイル自体が `BEGIN` 〜 `COMMIT`（`lock_timeout` 10 秒）。途中で失敗すれば何も変わらない。

## 既存データへの影響（行は変えない）

2026-10-21 の読み取り（`.runtime/PR1201_影響調査_2026-10-21.md`）で、本番の未来分:
- 未申込: 立方館 1 グループ・平日 10:00 の候補 5 件（2027-01-04〜08、大久保／馬場オフィス）。行は残るが、**この候補を含めて店舗へ申し込むと拒否**（「営業時間外です」）、**希望店舗を変えると 5 件が外れる**。昼・夜の候補に変えれば申し込める。必要なら主催者へ案内する。
- 申請中 1 件（11/5 木 10:00）・確定 7 件（平日 13:00 前開始）: 承認・確定・表示・キャンセルは営業時間を確かめないので、そのまま進む。取り下げて申し込み直す場合だけ拒否される。

## 適用の順序

1. **Codex レビュー**（修正・照合・復旧 SQL と試験）。
2. **staging に当てて確かめる**（一時的。staging は日次ミラーで本番の値に戻る）
   ```sh
   export PGHOST=db.lavutzztfqbdndjiwluc.supabase.co PGUSER=postgres PGDATABASE=postgres PGSSLMODE=require
   export PGPASSWORD="$(security find-generic-password -s supabase-db-staging -w)"
   psql -X -v ON_ERROR_STOP=1 -f supabase/data-fixes/20261021_queens_waltz_weekday_morning_off_check.sql   # 前（未適用・朝のある店 7）
   psql -X -v ON_ERROR_STOP=1 -f supabase/data-fixes/20261021_queens_waltz_weekday_morning_off.sql         # 「対象: 7 店・35 曜日」
   psql -X -v ON_ERROR_STOP=1 -f supabase/data-fixes/20261021_queens_waltz_weekday_morning_off_check.sql   # 後: changed が 35 行とも t、weekend_same・weekday_other_fields_same が全店 t、月〜金の朝のある店 0
   ```
   作品ページ（例: 立方館・作者不詳）で平日の朝が出ず、昼・夜と土日の朝が出ることを見る。
3. **本番に設定（データ修正）を当てる → 読み取りで確かめる**。**コード（#1201 の公開トップ入口の変更）より先に当てる。**
   理由: #1201 のコードを先に出すと、公開トップの入口に東京 7 店の平日朝が新しく出て、朝の露出が一時的に増える（今の本番の入口は開店時刻で朝を落としている）。
   ```sh
   export PGHOST=db.cznpcewciwywcqcxktba.supabase.co PGUSER=postgres PGDATABASE=postgres PGSSLMODE=require
   export PGPASSWORD="$(security find-generic-password -s supabase-db-prod -w)"
   psql -X -v ON_ERROR_STOP=1 -f supabase/data-fixes/20261021_queens_waltz_weekday_morning_off_check.sql
   psql -X -v ON_ERROR_STOP=1 --single-transaction -f supabase/data-fixes/20261021_queens_waltz_weekday_morning_off.sql
   psql -X -v ON_ERROR_STOP=1 -f supabase/data-fixes/20261021_queens_waltz_weekday_morning_off_check.sql
   ```
   - `--single-transaction` を付けても付けなくてもよい（ファイル自体が 1 取引。付けると最後に「there is no transaction in progress」の WARNING が出るだけ。手元 DB で確認済み）。
   - 「対象の曜日が N 件（見込み 35 件）」で止まったら、何も変わっていない。照合 SQL の結果を見て原因を調べる（設定画面で誰かが変えた等）。
   - 確認: 設定 › 店舗別 › 営業時間 で 7 店の月〜金の「朝」が消灯、土日の「朝」は点灯。作品ページで平日の朝が出ない。札幌店は変化なし。
4. **本番にコードを出す**: staging 全体ではなく、**#1201 の変更だけを `main` に cherry-pick した hotfix PR** を別に作って出す（作成は社長の GO の後。staging に未公開の他の変更を本番へ混ぜないため）。
   ```sh
   git fetch origin main && git switch -c hotfix/issue1200-private-morning-slot origin/main
   git cherry-pick <#1201 のコミット（staging への取り込み後の SHA）>
   npm run verify && npx vitest run
   gh pr create --base main ...
   ```
   出した後に、公開トップの入口（リスト・カレンダー）で東京 7 店の平日朝が出ないこと（設定で消灯済みのため）を見る。

## 問題があったときの復旧

```sh
psql -X -v ON_ERROR_STOP=1 -f supabase/data-fixes/20261021_queens_waltz_weekday_morning_off_rollback.sql
psql -X -v ON_ERROR_STOP=1 -f supabase/data-fixes/20261021_queens_waltz_weekday_morning_off_check.sql   # changed が全行 f、朝のある店 7 に戻る
```
- 書き戻すのは「今の値 = 退避した値に修正を当てた値」と一致する行だけ。修正の後に設定画面で営業時間を変えた店は上書きせず、`WARNING 店舗 … は修正後に営業時間が変えられているため書き戻さない` を出して飛ばす → その店は設定画面で平日の「朝」を手で点灯する。
- 2 回流しても同じ（2 回目は書き戻し 0 件）。`updated_at` は戻らない（復旧時刻になる）。
- コードを出した後に復旧すると、公開トップの入口にも東京 7 店の平日朝が出る（#1201 の仕様どおり）。
- 退避表は照合のため残す。不要になったら（例: 1 か月後）`DROP TABLE archive.business_hours_settings_backup_20261021;` を承認を得て流す。`archive` の表なので、消しても DB 構造の記録（`supabase/structure/*.json`）の更新は要らない。
