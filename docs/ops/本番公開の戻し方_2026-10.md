「取引」は、ファイルの中に `BEGIN;` / `COMMIT;` があるか。**なし** のものは、`psql -f` でそのまま流すと 1 文ずつ確定するので、

### 2. 1 本ずつ当てて、そのたびに履歴へ記録する

```bash
v=20261010100000
psql -X -1 -v ON_ERROR_STOP=1 -f supabase/migrations/${v}_*.sql && \
  SUPABASE_DB_PASSWORD="$PGPASSWORD" npx supabase migration repair --status applied "$v" --linked
```

`psql` は直接流すので履歴（`schema_migrations`）に残らない。`migration repair --status applied` で「当てた」と記録する。
記録しないと、(6) の自動配備が未適用と判断して止まる。

例外: `20261010130000` と `20261010160000` は、当てると定期実行と引き金が有効な状態で作られる。**同じ取引の中で止める**
（3 章の 1 の後半）。

### 3. 1 本ごとの確認

```sql
SELECT version FROM supabase_migrations.schema_migrations WHERE version = '<番号>';   -- 1 行
```

`psql` の出力に `ERROR` が無いこと（`ON_ERROR_STOP` で止まる）。`WARNING: there is already a transaction in progress` は
取引ありのファイルを `-1` で流したときの正常な警告。

### 4. N 本目で失敗したとき

`-1` で流していれば、失敗した N 本目は何も残っていない（取引ごと取り消し）。1〜N−1 本目は当たって記録済み。
画面はまだ旧画面なので、この状態でもお客様の操作は (a) のとおり動く。慌てて戻さない。

| 失敗の原因 | 判断 |
|---|---|
| ロック待ち（`lock_timeout`）・接続切れ・一時的な負荷 | 少し待って **N 本目から続ける**（同じコマンドをもう一度） |
| 本番のデータが前提と違う（制約違反など）で、migration の中身を直さないと通らない | その場で直さない。**1〜N−1 本目を新しい順に戻す**（下）。直した migration を staging で通してから出直す |
| 原因が分からない | 戻す。30 分以上「新しい DB ＋旧画面」のまま調べ続けない |

戻すときは、N−1 本目から 1 本目へ、1 本ずつ:

```bash
v=<戻す番号>
psql -X -1 -v ON_ERROR_STOP=1 -f supabase/rollbacks/${v}_*.sql && \
  SUPABASE_DB_PASSWORD="$PGPASSWORD" npx supabase migration repair --status reverted "$v" --linked
```

`--status reverted` は履歴の行を消すだけで、DB の中身は戻さない。中身は rollback の SQL で戻す（順番は「SQL → repair」）。
もし repair だけ済んで SQL が失敗した（またはその逆）ときは、下の SQL で実際の状態を見て、履歴を実態に合わせる。

```sql
-- 例: 20261020130000 が実際に当たっているか
SELECT count(*) FROM information_schema.columns WHERE table_name = 'coupon_usages' AND column_name = 'redeemed_at';
```

## 3. 通知の止め方・設定・再開

### 1. 止める（(1)、DB に当てる前）

本番に既にある定期実行（お客様へのお知らせメール）を止める。止めている間もメールは送信待ち（`customer_notice_emails`）に積まれ、消えない。

```sql
SELECT cron.alter_job(jobid, active := false) FROM cron.job WHERE jobname = 'process-customer-notice-emails';
SELECT jobname, active FROM cron.job WHERE jobname = 'process-customer-notice-emails';   -- f
```

ウェブプッシュの定期実行と引き金は、まだ本番に無い。`20261010130000`・`20261010160000` を当てるときに、同じ取引で止める。

```bash
# 3 本目
psql -X -1 -v ON_ERROR_STOP=1 -f supabase/migrations/20261010130000_private_group_web_push.sql \
  -c "SELECT cron.alter_job(jobid, active := false) FROM cron.job WHERE jobname IN ('process-web-push', 'private-group-guest-chat-digest')" \
  -c "ALTER TABLE public.private_group_messages DISABLE TRIGGER web_push_on_group_message" \
  -c "ALTER TABLE public.user_notifications DISABLE TRIGGER web_push_on_user_notification"
# 5 本目（web_push_on_user_notification を作り直すので、もう一度止める）
psql -X -1 -v ON_ERROR_STOP=1 -f supabase/migrations/20261010160000_private_group_memories.sql \
  -c "SELECT cron.alter_job(jobid, active := false) FROM cron.job WHERE jobname = 'private-group-memories-notice'" \
  -c "ALTER TABLE public.user_notifications DISABLE TRIGGER web_push_on_user_notification"
```

（それぞれの後に `migration repair --status applied` を忘れない。）29 本を当て終えたら確認:

```sql
SELECT jobname, active FROM cron.job
 WHERE jobname IN ('process-customer-notice-emails', 'process-web-push', 'private-group-guest-chat-digest', 'private-group-memories-notice');  -- 全部 f
SELECT tgname, tgenabled FROM pg_trigger WHERE tgname IN ('web_push_on_group_message', 'web_push_on_user_notification');  -- 全部 D
```

`private_group_on_date_response`（日程がそろったときのベル・メール）は止めない。メールは送信待ちに積まれるだけで、送るのは (8) の後。
なお、画面を出すまで購読（`web_push_subscriptions`）は 0 件なので、ウェブプッシュは仕組み上まだ誰にも届かない。

### 2. 設定と配備（(5)）

名前だけ書く。値は 1Password／Keychain から入れ、画面やチャットに出さない。

| 置き場所 | 名前 | 使うところ |
|---|---|---|
| Supabase secrets（本番） | `VAPID_PUBLIC_KEY`・`VAPID_PRIVATE_KEY`・`VAPID_SUBJECT` | `send-web-push` の署名 |
| Supabase secrets（本番） | `WEB_PUSH_CRON_SECRET` | `send-web-push` が DB からの呼び出しを確かめる。DB の `app_config.trigger_secret` と同じ値 |
| Supabase secrets（本番） | `CRON_SECRET`（無ければ `EDGE_FUNCTION_CRON_SECRET`） | `process-customer-notice-emails` が DB からの呼び出しを確かめる。`app_config.trigger_secret` と同じ値であること |
| Vercel（Production） | `VITE_VAPID_PUBLIC_KEY` | 画面が購読するときの公開鍵。`VAPID_PUBLIC_KEY` と同じ値 |

注: 依頼文にあった `CUSTOMER_NOTICE_CRON_SECRET` という名前はコードに無い。お知らせメールの関数は `_shared/security.ts` の
`CRON_SECRET`（無ければ `EDGE_FUNCTION_CRON_SECRET`）で確かめる。staging では `CRON_SECRET` と `trigger_secret` が別の値で
401 になる見込みと記録がある（`docs/IMPROVEMENT_HANDOFF.md`）。本番も名前と一致を確かめる（値を見ずに確かめるには、
(7) で 1 件送って 401 が出ないことを見る）。

順序:

## 5. 戻すとき: 先に決めること（どこまで戻すか）

| 症状 | 戻す範囲 | データ |
|---|---|---|
| 画面の不具合（表示崩れ・操作できない） | 画面だけ（A） | 何も消えない |
| プッシュ通知の誤送信・送りすぎ | 通知の止血（A-2）。画面は戻さなくてよい | 何も消えない |
| DB の関数・トリガーが原因で予約や承認が止まる | DB まで（B） | 退避してから消す |

**まず A（画面だけ）で済まないかを考える。** B は新しい表を消すので、退避を必ず先に行う。

## (a) 画面（Vercel）だけ戻す場合の DB 互換性

新しい表・列は残ったまま、旧画面が動く。旧画面は新しい表を読まず、足された列は無視する。
旧画面が呼ぶ関数は、引数が増えたものも既定値つきなので、そのまま通る（`create_private_booking_request` 等）。
2026-10-20 以降の 9 本（`20261020120000`〜`20261020220000`）も、関数の中身の入れ替え・列の追加・設定の追加だけで、引数を消すものは無い。
ただし `20261020190000` 以降は、旧画面からでも「予約後にクーポンを当てる」操作が公演当日だけになる（決まりの変更なので想定どおり）。
`20261012140000` で消える `admin_recalculate_reservation_prices(uuid)` は、旧 API も引数 2 つの版を呼んでいるので影響しない。

ただし、旧画面では次の見え方になる（壊れはしないが、お客様が戸惑う）。

1. **新しい種類のお知らせが中身のまま出る。** 旧画面のチャットは知らない種類のお知らせを普通の発言として表示するため、
   `{"type":"system","action":"date_answer_reminder",...}` のような文字列がそのまま見える。
   対象: `date_answer_reminder`（未回答の人に知らせる）、`next_group_created`（同じメンバーで次の貸切）。
2. **削除した発言が空の吹き出しになる。** 削除すると本文は空にされ、旧画面は「削除済み」を知らない。
3. **写真だけの発言が空の吹き出しになる。** 写真は旧画面に出ない（ファイルは残る。`/api/private-group-photos` が無くなるので誰も開けない）。
   写真に添えた文は文だけ出る。
4. **返信先・ピン留め・リアクション・既読は見えなくなる。** 記録は残り、画面を戻し直せばまた見える。
5. **通知は送られ続ける。** プッシュ（`process-web-push` 毎分、トリガーからの即時送信）、
   ゲストへの未読まとめメール（`private-group-guest-chat-digest` 毎朝 9 時）、
   「写真を共有しませんか」のベルとプッシュ（`private-group-memories-notice` 毎朝 10 時）。
   旧画面にはプッシュを止める設定も写真の機能も無いので、画面を戻すときは下の A-2 で止める。

## (b) DB まで戻す場合に先に退避するもの

rollback を逆順に機械的に流すと、公開後に入ったお客様のデータが消える。
2026-10-20 から、該当 3 本の rollback は **消す前に非公開スキーマ `rollback_backup` へ自動で写す** ようにした
（2026-10-21 に `20261020130000` の来店確認の列も追加して 4 本）
（表名は `<元の表名>_backup_<JST の日付>`、ブラウザの役割からは読めない。同じ日の退避が既にあれば止まり、何も消さない）。

| rollback | 退避される表 | 退避される列 |
|---|---|---|
| `20261020130000_coupon_usage_redeem` | なし | `coupon_usages` の `redeemed_at`・`redeemed_by_member`・`redeemed_source`（印のある行だけ。`coupon_usages_redeem_backup_<日付>`） |
| `20261010160000_private_group_memories` | `private_group_feedback`（感想） | `private_group_message_photos.thumb_path`（値のある行だけ。`private_group_message_photos_thumb_backup_<日付>`） |
| `20261010130000_private_group_web_push` | `web_push_subscriptions`（端末の購読）、`private_group_notification_settings`（グループごとの ON/OFF）、`web_push_outbox`（送信の記録） | なし |
| `20261010100000_private_group_chat_phase2` | `private_group_message_photos`（写真の記録）、`private_group_message_reactions`、`private_group_read_states`（既読） | `private_group_messages` の `reply_to_message_id`・`deleted_at`・`pinned_at`・`pinned_by_member_id`（値のある行だけ。`private_group_messages_cols_backup_<日付>`） |

**退避しても元に戻らないもの・失うもの**（rollback を流す前に社長へ伝える）:

- **削除済みの発言の本文。** 削除した時点で本文は空にされている（rollback とは関係なく戻らない）。rollback 後は「削除済み」の印も
  退避側にだけ残り、旧画面では空の吹き出しに見える。
- **送ってしまった通知。** 送信の記録は退避されるが、届いたプッシュやメールは取り消せない。
- **定期実行の設定。** `process-web-push`・`private-group-guest-chat-digest`・`private-group-memories-notice` は rollback で消える。
  当て直すと作り直されるが、`app_config` の接続設定が欠けていると `process-web-push` は作られない（当て直し後に `cron.job` を確認）。
- **退避した後に入った記録。** rollback を流してから当て直すまでの間に新しい表へ書かれるものは無い（表が無いので書けない）が、
  旧画面で行った操作（発言・日程回答）は新しい表に反映されない（既読・リアクションなどは付かない）。
- **写真のファイル。** SQL では消えない（下）。記録は退避から戻せるが、ファイルを誰かが消すと戻らない。

自動退避の対象外で、手で残すもの:

- **Storage `private-group-photos` の写真ファイル。** SQL からは消せない（rollback もバケットは中身が空のときだけ消す）ので
  残るが、誰かが管理画面で空にする前に手元へ写しておく。

  ```bash
  # 本番（cznpcewciwywcqcxktba）の写真を手元へ。読み取りだけ
  npx supabase storage cp -r ss:///private-group-photos ./backup-2026xxxx/private-group-photos \
    --project-ref cznpcewciwywcqcxktba -j 4
  find ./backup-2026xxxx/private-group-photos -type f | wc -l   # 下の件数と見比べる
  ```

  ```sql
  SELECT count(*) FROM storage.objects WHERE bucket_id = 'private-group-photos';
  ```

- **同じ公開分のほかの rollback が消す列。** `20261012110000` は `private_group_message_photos.byte_size`
  （ファイルの大きさから作り直せるので退避不要）、`20261011210000` は `stores.public_name`（店舗の公開名。
  公開後に管理画面で入力した値があれば消える）。後者を戻すなら先に写す:

  ```sql
  CREATE SCHEMA IF NOT EXISTS rollback_backup;
  CREATE TABLE rollback_backup.stores_public_name_backup_2026xxxx AS
    SELECT id, organization_id, public_name FROM public.stores WHERE public_name IS NOT NULL;
  REVOKE ALL ON rollback_backup.stores_public_name_backup_2026xxxx FROM PUBLIC, anon, authenticated;
  ```

- **念のための全体退避。** 戻す直前に、管理画面の Database → Backups で最新の日次バックアップの時刻を控える
  （PITR が有効ならその時刻）。

退避した記録を戻すとき（migration を当て直した後。`2026xxxx` を退避した日付に差し替え、1 つの取引で流す）:

```sql
BEGIN;
-- 1. 表ごと退避したもの: 今の表にもある列だけを写す（列の並びが変わっていても通る）。重なる行は今の表を優先
DO $restore$
DECLARE d text := '2026xxxx'; t text; b text; cols text;
BEGIN
  FOREACH t IN ARRAY ARRAY['private_group_message_photos', 'private_group_message_reactions', 'private_group_read_states',
                           'web_push_subscriptions', 'private_group_notification_settings', 'web_push_outbox', 'private_group_feedback'] LOOP
    b := t || '_backup_' || d;
    IF to_regclass(format('rollback_backup.%I', b)) IS NULL THEN CONTINUE; END IF;
    SELECT string_agg(quote_ident(bc.column_name), ', ' ORDER BY bc.ordinal_position) INTO cols
      FROM information_schema.columns bc
      JOIN information_schema.columns pc ON pc.table_schema = 'public' AND pc.table_name = t AND pc.column_name = bc.column_name
     WHERE bc.table_schema = 'rollback_backup' AND bc.table_name = b;
    EXECUTE format('INSERT INTO public.%I (%s) SELECT %s FROM rollback_backup.%I ON CONFLICT DO NOTHING', t, cols, cols, b);
    RAISE NOTICE '書き戻し: %', t;
  END LOOP;
END $restore$;
-- 2. 既読は当て直しのときに「今読んだ」で作り直されるので、退避の時刻で上書きする
UPDATE public.private_group_read_states r SET last_read_at = b.last_read_at, updated_at = b.updated_at
  FROM rollback_backup.private_group_read_states_backup_2026xxxx b WHERE b.group_id = r.group_id AND b.member_id = r.member_id;
-- 3. 退避した送信待ちは送らない（古い通知が一斉に届かないように）
UPDATE public.web_push_outbox SET status = 'skipped', skip_reason = 'restored_after_rollback' WHERE status = 'pending';
-- 4. 列だけ退避したもの
UPDATE public.private_group_messages m SET reply_to_message_id = b.reply_to_message_id, deleted_at = b.deleted_at,
  pinned_at = b.pinned_at, pinned_by_member_id = b.pinned_by_member_id
  FROM rollback_backup.private_group_messages_cols_backup_2026xxxx b WHERE b.id = m.id;
UPDATE public.private_group_message_photos p SET thumb_path = b.thumb_path
  FROM rollback_backup.private_group_message_photos_thumb_backup_2026xxxx b WHERE b.message_id = p.message_id AND b.position = p.position;
UPDATE public.coupon_usages u SET redeemed_at = b.redeemed_at,
  redeemed_by_member = (SELECT c.id FROM public.customers c WHERE c.id = b.redeemed_by_member), redeemed_source = b.redeemed_source
  FROM rollback_backup.coupon_usages_redeem_backup_2026xxxx b WHERE b.usage_id = u.id AND u.redeemed_at IS NULL;
-- 5. 写真の大きさ（byte_size）を小さい版も含めて数え直す
UPDATE public.private_group_message_photos p SET byte_size = (SELECT coalesce(sum(nullif(o.metadata->>'size', '')::bigint), 0)
  FROM storage.objects o WHERE o.bucket_id = 'private-group-photos' AND o.name IN (p.storage_path, p.thumb_path));
COMMIT;
```

写真の記録は、先にファイルが Storage に戻っていること。写真の枚数上限の引き金（`private_group_message_photo_enforce_limit`）で
止まったときは、その取引の中だけ `ALTER TABLE public.private_group_message_photos DISABLE TRIGGER private_group_message_photo_enforce_limit;`
を先頭に足し、最後に `ENABLE` する（退避した写真は元々上限の内側で投稿されたもの）。

### 2. 画面（Vercel）

### 3. DB

   ```bash
     SUPABASE_DB_PASSWORD="$PGPASSWORD" npx supabase migration repair --status reverted "$v" --linked
   ```

   一部だけ戻すときも、戻したい migration より新しいものから順に流す。表や列を消す 5 本（1 章の表で太字）は、
   流す前に (b) の手で残すものを済ませ、流した後に `NOTICE: 退避しました` の行数を控える。
4. 確認:

   ```sql
   -- 退避ができていること（件数が元の表と同じ）
   SELECT c.relname, c.reltuples FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace WHERE n.nspname = 'rollback_backup';
   -- 新しい表が無くなったこと
   SELECT to_regclass('public.private_group_message_photos'), to_regclass('public.web_push_outbox'), to_regclass('public.private_group_feedback');
   SELECT count(*) FROM information_schema.columns WHERE table_name = 'coupon_usages' AND column_name LIKE 'redeemed%';  -- 0
   -- 定期実行が残っていないこと
   SELECT jobname FROM cron.job WHERE jobname IN ('process-web-push', 'private-group-guest-chat-digest', 'private-group-memories-notice');
   ```

   画面では、グループページのチャット送信・日程回答・貸切申込・店舗側の承認を 1 回ずつ通す（staging の点検手順と同じ）。
5. `rollback_backup` の表は、原因を直して当て直すまで消さない。不要になったら社長の承認を得てから `DROP SCHEMA rollback_backup CASCADE`。

## (d) 復元リハーサルの提案（今回は実施しない）

1. **staging で旧画面＋新 DB を確かめる。** `main` の画面を staging の DB につないだプレビューで、(a) の 1〜5 が想定どおりか、
   ほかに壊れる所が無いかを見る（Vercel の Preview に staging の環境変数を付けて `main` を配備）。
2. **staging で DB の戻しを通しで流す。** 上の順序で全部流し、退避の件数と、退避からの書き戻し（(b) の INSERT/UPDATE）を確かめる。
   その後 migration を当て直して staging を元に戻す。2026-10-20 に手元の DB で、該当 7 本を 1 つの取引で流して最後に取り消す形で、
   退避（9 表）・同日の二重退避の停止・ブラウザの役割から読めないことは確認済み。2026-10-21 に Codex が本番の構造で 29 本の
   当てる → 戻す → 当て直すを通した（来店確認の記録の欠けはこのときに見つけて 4 章で直した）。
3. **本番バックアップからの復元を別プロジェクトで練習する。** 管理画面の「Restore to a new project」で本番の日次バックアップを
   新しいプロジェクトに戻し、所要時間と、Storage のファイルが含まれない（DB だけ戻る）ことを確かめる。費用がかかるので社長の承認を得て行う。
