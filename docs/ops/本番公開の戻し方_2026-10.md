# 本番公開の戻し方（2026-10 貸切グループページ刷新）

作成: 2026-10-20（外部監査 R5 への対応）。対象は、staging にあって本番にまだ無い次の公開分。

- DB: `20261010100000`（チャット強化と写真）、`20261010100100`、`20261010130000`（ウェブプッシュ）、`20261010130100`、
  `20261010160000`（公演後の思い出）、`20261011150000`〜`20261012140000`、`20261015110000`、`20261020100000`、`20261020110000`
  （2026-10-20 時点。本番の `supabase_migrations.schema_migrations` に無いもの。公開直前にもう一度突き合わせる）
- 画面と API（Vercel）: `api/private-group-photos.ts` ほか、グループページ・マイページ一式
- Edge Functions: 新規 `send-web-push`。`_shared` の変更で `process-customer-notice-emails`・`process-survey-reminders`・
  `send-booking-confirmation`・`send-cancellation-confirmation`・`send-contact-inquiry`・`send-guest-pin` なども配備し直しになる

この文書で言う「旧画面」は、公開前の本番の画面（`main` ブランチ）のこと。

---

## 先に決めること: どこまで戻すか

| 症状 | 戻す範囲 | データ |
|---|---|---|
| 画面の不具合（表示崩れ・操作できない） | 画面だけ（A） | 何も消えない |
| プッシュ通知の誤送信・送りすぎ | 通知の止血（A-2）。画面は戻さなくてよい | 何も消えない |
| DB の関数・トリガーが原因で予約や承認が止まる | DB まで（B） | 退避してから消す |

**まず A（画面だけ）で済まないかを考える。** B は新しい表を消すので、退避を必ず先に行う。

---

## (a) 画面（Vercel）だけ戻す場合の DB 互換性

新しい表・列は残ったまま、旧画面が動く。旧画面は新しい表を読まず、足された列は無視する。
旧画面が呼ぶ関数は、引数が増えたものも既定値つきなので、そのまま通る（`create_private_booking_request` 等）。
`20261012140000` で消える `admin_recalculate_reservation_prices(uuid)` は、旧 API も引数 2 つの版を呼んでいるので影響しない。

ただし、旧画面では次の見え方になる（壊れはしないが、お客様が戸惑う）。

1. **新しい種類のお知らせが中身のまま出る。** 旧画面のチャットは知らない種類のお知らせを普通の発言として表示するため、
   `{"type":"system","action":"date_answer_reminder",...}` のような文字列がそのまま見える。
   対象: `date_answer_reminder`（未回答の人に知らせる）、`next_group_created`（同じメンバーで次の貸切）。
2. **削除した発言が空の吹き出しになる。** 削除すると本文は空にされ、旧画面は「削除済み」を知らない。
3. **写真だけの発言が空の吹き出しになる。** 写真は旧画面に出ない（ファイルは残る。`/api/private-group-photos` が無くなるので誰も開けない）。
   写真に添えた文は文だけ出る。
4. **返信先・ピン留め・リアクション・既読は見えなくなる。** 記録は残り、画面を戻し直せばまた見える。
5. **通知は送られ続ける。** プッシュ（`process-web-push` 毎分、トリガーからの即時送信）、
   ゲストへの未読まとめメール（`private-group-guest-chat-digest` 毎朝 9 時）、
   「写真を共有しませんか」のベルとプッシュ（`private-group-memories-notice` 毎朝 10 時）。
   旧画面にはプッシュを止める設定も写真の機能も無いので、画面を戻すときは下の A-2 で止める。

### A. 画面だけ戻す手順

1. Vercel の管理画面で、公開前の本番の配備（Production の 1 つ前）を「Instant Rollback」で戻す。
   CLI なら `vercel rollback <公開前の配備URL>`。
2. 確認: 本番のグループページを開き、チャット・日程回答・申込が旧画面で動くこと。上の 1〜3 の見え方は想定どおり。
3. 下の A-2 で通知を止める。

### A-2. 通知の止血（データを消さない）

```sql
-- 定期実行を一時停止（消さない。戻すときは active := true）
SELECT cron.alter_job(jobid, active := false) FROM cron.job
 WHERE jobname IN ('process-web-push', 'private-group-guest-chat-digest', 'private-group-memories-notice');
-- 発言・ベルからの即時プッシュを止める（トリガーは残して無効にするだけ）
ALTER TABLE public.private_group_messages DISABLE TRIGGER web_push_on_group_message;
ALTER TABLE public.user_notifications DISABLE TRIGGER web_push_on_user_notification;
```

確認:

```sql
SELECT jobname, active FROM cron.job WHERE jobname IN ('process-web-push', 'private-group-guest-chat-digest', 'private-group-memories-notice');
SELECT tgname, tgenabled FROM pg_trigger WHERE tgname IN ('web_push_on_group_message', 'web_push_on_user_notification'); -- D なら無効
SELECT status, count(*) FROM public.web_push_outbox WHERE created_at > now() - interval '10 minutes' GROUP BY 1; -- 増えないこと
```

`private_group_on_date_response`（日程がそろったときのベル・メール）は旧画面でも意味が通じるので止めない。

## (b) DB まで戻す場合に先に退避するもの

rollback を逆順に機械的に流すと、公開後に入ったお客様のデータが消える。
2026-10-20 から、該当 3 本の rollback は **消す前に非公開スキーマ `rollback_backup` へ自動で写す** ようにした
（表名は `<元の表名>_backup_<JST の日付>`、ブラウザの役割からは読めない。同じ日の退避が既にあれば止まり、何も消さない）。

| rollback | 退避される表 | 退避される列 |
|---|---|---|
| `20261010160000_private_group_memories` | `private_group_feedback`（感想） | `private_group_message_photos.thumb_path`（値のある行だけ） |
| `20261010130000_private_group_web_push` | `web_push_subscriptions`（端末の購読）、`private_group_notification_settings`（グループごとの ON/OFF）、`web_push_outbox`（送信の記録） | なし |
| `20261010100000_private_group_chat_phase2` | `private_group_message_photos`（写真の記録）、`private_group_message_reactions`、`private_group_read_states`（既読） | `private_group_messages` の `reply_to_message_id`・`deleted_at`・`pinned_at`・`pinned_by_member_id`（値のある行だけ） |

自動退避の対象外で、手で残すもの:

- **Storage `private-group-photos` の写真ファイル。** SQL からは消せない（rollback もバケットは中身が空のときだけ消す）ので
  残るが、誰かが管理画面で空にする前に手元へ写しておく。

  ```bash
  # 本番（cznpcewciwywcqcxktba）の写真を手元へ。読み取りだけ
  npx supabase storage cp -r ss:///private-group-photos ./backup-2026xxxx/private-group-photos \
    --project-ref cznpcewciwywcqcxktba -j 4
  find ./backup-2026xxxx/private-group-photos -type f | wc -l   # 下の件数と見比べる
  ```

  ```sql
  SELECT count(*) FROM storage.objects WHERE bucket_id = 'private-group-photos';
  ```

- **同じ公開分のほかの rollback が消す列。** `20261012110000` は `private_group_message_photos.byte_size`
  （ファイルの大きさから作り直せるので退避不要）、`20261011210000` は `stores.public_name`（店舗の公開名。
  公開後に管理画面で入力した値があれば消える）。後者を戻すなら先に写す:

  ```sql
  CREATE SCHEMA IF NOT EXISTS rollback_backup;
  CREATE TABLE rollback_backup.stores_public_name_backup_2026xxxx AS
    SELECT id, organization_id, public_name FROM public.stores WHERE public_name IS NOT NULL;
  REVOKE ALL ON rollback_backup.stores_public_name_backup_2026xxxx FROM PUBLIC, anon, authenticated;
  ```

- **念のための全体退避。** 戻す直前に、管理画面の Database → Backups で最新の日次バックアップの時刻を控える
  （PITR が有効ならその時刻）。

退避した記録を戻すとき（migration を当て直した後）:

```sql
INSERT INTO public.private_group_feedback SELECT * FROM rollback_backup.private_group_feedback_backup_2026xxxx ON CONFLICT DO NOTHING;
UPDATE public.private_group_messages m SET reply_to_message_id = b.reply_to_message_id, deleted_at = b.deleted_at,
  pinned_at = b.pinned_at, pinned_by_member_id = b.pinned_by_member_id
  FROM rollback_backup.private_group_messages_cols_backup_2026xxxx b WHERE b.id = m.id;
-- ほかの表も同じ形（列の並びは元の表と同じ）。写真の記録は先にファイルが Storage に戻っていること
```

## (c) 戻す順序（Edge → 画面 → DB）と確認

DB は最後。Edge と画面を先に戻しておけば、DB を戻す間に新しい関数を呼ぶものが無くなる。

### 1. Edge Functions

- `main` を checkout して、変更のあった関数を `main` の中身で配備し直す（`.github/workflows/deploy-supabase.yml` の手動実行で
  environment を production にするか、`supabase functions deploy <名前> --project-ref cznpcewciwywcqcxktba`。
  `--no-verify-jwt` の要否はワークフローの一覧に従う）。
- `send-web-push` は旧版が無い。DB を戻さないなら残す（A-2 で止まる）。DB も戻すなら最後に
  `supabase functions delete send-web-push --project-ref cznpcewciwywcqcxktba`。
- 確認: 管理画面の Edge Functions で各関数の版が上がったこと。ログで 401/500 が増えていないこと
  （管理 API `GET /v1/projects/{ref}/analytics/endpoints/logs`、`source='function_edge_logs'`）。

### 2. 画面（Vercel）

上の A の手順。確認も同じ。

### 3. DB

1. A-2 の通知止血を先に行う（rollback の途中で送られないように）。
2. (b) の手で残すもの（Storage・`stores.public_name`）を写す。
3. rollback を **新しい順に** 1 本ずつ、本番の SQL Editor で流す。

   ```
   20261020110000 → 20261020100000 → 20261015110000 → 20261012140000 → 20261012130000 → 20261012120000
   → 20261012110000 → 20261012100000 → 20261011220000 → 20261011210000 → 20261011200000 → 20261011190000
   → 20261011180000 → 20261011170000 → 20261011150000 → 20261010160000 → 20261010130100 → 20261010130000
   → 20261010100100 → 20261010100000
   ```

   一部だけ戻すときも、戻したい migration より新しいものから順に流す（後の migration が前の表や関数を前提にしている）。
   流すたびに履歴から消す: `DELETE FROM supabase_migrations.schema_migrations WHERE version = '<番号>';`
4. 確認:

   ```sql
   -- 退避ができていること（件数が元の表と同じ）
   SELECT c.relname, c.reltuples FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace WHERE n.nspname = 'rollback_backup';
   -- 新しい表が無くなったこと
   SELECT to_regclass('public.private_group_message_photos'), to_regclass('public.web_push_outbox'), to_regclass('public.private_group_feedback');
   -- 定期実行が残っていないこと
   SELECT jobname FROM cron.job WHERE jobname IN ('process-web-push', 'private-group-guest-chat-digest', 'private-group-memories-notice');
   ```

   画面では、グループページのチャット送信・日程回答・貸切申込・店舗側の承認を 1 回ずつ通す（staging の点検手順と同じ）。
5. `rollback_backup` の表は、原因を直して当て直すまで消さない。不要になったら社長の承認を得てから `DROP SCHEMA rollback_backup CASCADE`。

## (d) 復元リハーサルの提案（今回は実施しない）

1. **staging で旧画面＋新 DB を確かめる。** `main` の画面を staging の DB につないだプレビューで、(a) の 1〜5 が想定どおりか、
   ほかに壊れる所が無いかを見る（Vercel の Preview に staging の環境変数を付けて `main` を配備）。
2. **staging で DB の戻しを通しで流す。** 上の順序で全部流し、退避の件数と、退避からの書き戻し（(b) の INSERT/UPDATE）を確かめる。
   その後 migration を当て直して staging を元に戻す。2026-10-20 に手元の DB で、該当 7 本を 1 つの取引で流して最後に取り消す形で、
   退避（9 表）・同日の二重退避の停止・ブラウザの役割から読めないことは確認済み。
3. **本番バックアップからの復元を別プロジェクトで練習する。** 管理画面の「Restore to a new project」で本番の日次バックアップを
   新しいプロジェクトに戻し、所要時間と、Storage のファイルが含まれない（DB だけ戻る）ことを確かめる。費用がかかるので社長の承認を得て行う。
