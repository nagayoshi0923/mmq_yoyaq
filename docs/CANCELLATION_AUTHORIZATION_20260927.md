# 取消処理の本人確認・店舗専用フラグ

案件 QW-20260917-001。全領域棚卸しは対応中。

## 確認した不具合と修正

本番の3引数 `cancel_reservation_with_lock` と `cancel_reservation_and_group_with_lock` は、送信された `p_customer_id` が本人の顧客IDなら、対象予約との対応を確認せず本人扱いしていた。APIは予約の実顧客IDを渡すが、認証済み利用者はRPCを直接呼べるためAPIだけでは防げない。

本人判定を予約の `customer_id` に固定した。既存の引数は互換性のため保持し、同組織管理者・有効スタッフの判定は変更しない。2引数版は元から予約の実顧客で判定している。ACL・RLS変更なし。

APIの `skip_group_cancel` と `cancel_private_event` は店舗の却下操作用であるため、予約の取得・更新前にスタッフ権限を検証する。通常の顧客取消は既存の本人確認と取消期限の判定を通る。

## 検証

隔離PGliteで読み取った本番旧定義を実行し、自己顧客ID差し替えによる他予約の取消を再現。修正後は両RPCで拒否し、予約・グループ・人数が変化しないことを確認した。無効スタッフ、他組織スタッフ・管理者、未認証も拒否。実予約者、有効スタッフ、同組織管理者は既存どおり取消できる。API7件で店舗専用フラグの顧客拒否と通常導線を確認。

実際の予約取消・公演中止・通知は行っていない。DB適用・本番反映・受入は未実施。
